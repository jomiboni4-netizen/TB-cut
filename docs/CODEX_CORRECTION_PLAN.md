## 不可突破的修正节奏

- **至少 3 轮、至多 5 轮 Codex 代码修正，之后由用户决定并执行实测。** 一轮=可审查的源码与合成测试改动 + 单独提交 + 回归结果 + 未解决事项。纯文档提交不计入轮次。
- 第 3 轮后评估是否具备实测条件；确有阻塞才进行第 4、5 轮。第 5 轮停止无止境修正：交付候选版本及风险清单，若仍不满足硬规则，则报告阻塞而非擅自实测或无限续轮。
- 开发期间允许合成测试、单元测试、离线 dry-run；使用真实媒体、外部 MiMo、Resolve 写入或导出属于**独立授权**。不得以本计划视为实测授权。

## 项目绑定、缓存隔离和分段完成策略（P0，待实现）

**用户路径含义：** 一次指定的文件夹属于**整个达芬奇项目**，不是某一商品、某一轮 Codex 或临时小批次。首次登记并核对该项目的素材集合、SRT、标题表、Resolve 项目/源时间线/目标时间线、工作区身份及来源；接手新窗口和继续剩余商品时默认继承。同项目遇到新增或缺失输入只精准询问缺项并验证，不重复索要整目录。切换项目必须显式切换项目身份和工作区；绝不能仅凭目录同名判定同一项目。

**现有代码中的风险（已提交源码审阅，不等于本机已发生）：**

- `scripts/runtime_paths.py:26–47,71–75`：运行状态、`.cache/`、报告与导出放在统一 workspace，未建立不可混淆的项目级注册目录。
- `scripts/runtime_meta.py:151–163,217–224`：身份包含 `batch_id` 与输入/规则/范围摘要；跨处理批次复用可能被拒绝，不能简单移除身份检查以“加速”。
- `scripts/refine_plans_v2.py:166–170,266–301`：按 `product_XX_windowed/` 固定命名生成方案、汇总审核。不同项目或同一商品的新旧修订若共用工作区，存在路径互相覆盖的结构性风险。
- `scripts/person_coverage_audit_v2.py:87–96`、`scripts/resolve_write_v2.py:298–300`：存在固定全局输出名，须区分不同执行、方案和审核版本。
- `scripts/init_project.py:23–38`：使用状态模板初始化，已有状态默认拒绝覆盖，但没有“整项目登记一次 + 自动继承完整素材映射”的专用入口。
- `scripts/update_batch_state.py:24–38`：只维护完成/失败集合，缺少带审核来源/版本的逐商品 checkpoint 与整项目完成判定。

**目标数据边界（实现前不得当成现状）：**

1. `project_key`：由被确认的 Resolve 项目和工作区绑定，不随 Codex 窗口或商品组变化；不以展示项目名作为唯一依据。项目级输入清单与有效签名可独立更新和核对。
2. `run_id`：一次处理/恢复会话的独立身份；`group_id`：该 run 内小组；`product_index` 与 `encoding_id`：商品身份；`variant_id`、`stage`、`plan_digest`：衍生成果身份。不能用 `product_01` 或 `approved_plans.json` 单一名称跨项目/修订复用。
3. 保留稳定上游：源字幕/标题索引、经确认的商品范围独立于处理分组；小组重试只重算确实失效的商品级语义、切点与审核。ASR/人物检测缓存按精确媒体签名+源范围+模型/算法参数与版本内容寻址；只在依赖匹配时复用。
4. 运行级清单、全局人物审核、写入与导出报告按项目/运行/审查摘要定位，避免新执行覆盖旧报告；写入前使用锁、快照、临时文件、签名验证、幂等标记与当前时间线回读，处理失败不得自动覆盖/删除或“重新认证”旧缓存。
5. 产品进度账本至少记录：`PENDING`、`IN_PROGRESS`、`REPAIRABLE`、`BLOCKED`、`SEMANTIC_PASS`、`FINAL_PASS`、`WRITTEN`、`EXPORT_VERIFIED`（可细分）；状态依附对应审核/方案摘要。失败或修改上游时只撤销依赖受影响的结果，并列出安全恢复入口。
6. **全项目请求 = 全目标清单**；内部默认每组 2–3 款（初始建议，后续按实际质量调参）。当前组全部可适用的硬审、Codex 最终语义审核及适用的写入回读门禁通过，才处理下一组。一个商品达不到硬规则时不能为了吞吐强行放行；停止相关写入、保存问题及已完成成果，允许在明确安全隔离后继续分析其他未受影响的商品。
7. 最终整项目必须检查目标商品覆盖率、分组间重复/重叠、审核版本、实际时间线写入与音画同步，并区分已剪辑、已写入、已导出、已验证。无完整证据绝不报告“全部完成”。

**回归场景：** 两个 Resolve 项目都有编号 1 商品；同项目两次不同 group/run；新窗口接手；新增/遗漏源文件；并发生成和中途中断；旧审核伴随新切点；旧完成状态错配当前方案；同名聚合审核覆盖；已有 Resolve 标记时幂等重试；最终只有部分商品通过时报告全项目未完成。仅使用脱敏合成 fixtures，不读取真实项目数据。

**节奏边界：** 缓存与整项目调度并入既定的 3–5 轮 Codex 代码修正总预算；不是新开 3–5 轮。用户授权实测后再测真实跨窗口续剪与整项目质量。

## 人物检测建议算法（设计目标，尚未在当前远端代码实现）

1. **时间分层而非逐帧**：按最终物理片段的累计时长建立分层时间轴，初始每 60 秒抽 `N=16` 个分布均匀、位置带固定种子抖动的点；不足/超过一分钟按时长比例增减，确保每个有时长的源片段得到合理覆盖。映射回实际源帧，按媒体去重并缓存。
2. **逐轮追加未取过的点**：只有充分可信的高比例才提前放行。比例低于或接近 70%、样本过少、镜头变化明显或检测不确定时，再追加约 N 个不重复点；每轮在上一轮样本基础上重新计算。最多五次采样轮次，避免重读同一帧。
3. **保守判定**：硬门槛保持严格 `host_visible_ratio > 0.70`。优先使用一侧 95% Wilson 下界高于 0.70 作为早期 PASS 条件；该区间是抽样近似、不等同于全片证明。未形成可靠下界或检测存在环境异常时，不得标记 PASS。若已能可靠判定不满足则返回 REPAIRABLE；到采样上限仍模糊则 `UNCERTAIN/REPAIRABLE` 并申请局部复核，而非强行放行。
4. **分清主播与任意人物**：仅符合主播主体的画面计入；衣服特写、无人物、远景不确定或检测异常都不直接算主播。Apple Vision 结果不可靠时可针对小量模糊样本启动已授权本地 Qwen 回退；错误中止并记录，不可把异常当“无人”样本或 PASS。
5. **可量化对照**：合成测试覆盖刚超过/刚低于 70%、长短片段、来源切换、样本重复、探测失败、分辨率/帧率差异。授权后的实测与密集抽样基准作比对，分别报告调用次数、误放行风险、总耗时及是否漏掉局部无人区；未实测前不得宣称准确率或性能提升。
