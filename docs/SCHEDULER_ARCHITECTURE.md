# 双项目剪辑调度器

淘宝与都督使用两个用户可见的入口，底层共享状态校验与模块调用器：

- `scripts/taobao_scheduler.py`：路由至 `project_scheduler.py` 的完整商品选择、分析和质量审核链。
- `scripts/dudu_scheduler.py`：路由至 `delivery_pipeline.py` 的标记范围、ASR、组装、语义/人物门禁与逐款交付阶段。
- `scripts/workflow_scheduler.py`：读取当前批次项目名，按 `project_editing_modes.py` 唯一匹配模式，检查入口身份并记录/分派工作。模式和现有模块关系集中在 `WORKFLOWS`；具体剪辑计算仍由原模块负责。

Codex 应先调用对应入口的 `plan`，再调用 `run`。`plan` 会在当前 workspace 写入绑定项目名、项目批次、模式和阶段图的 `SCHEDULER_PLAN.json`；`run` 必须验证该计划仍与当前身份和配置相符，变更后需重新生成。失败后调用 `diagnose`，根据返回的错误、有效阶段、`rollback_to`、`preserve` 和 `invalidate` 修复模块并恢复；不能凭自然语言猜测从头重跑，也不能手工清缓存。不能只凭自然语言自行更换项目或时间线。入口会拒绝模式不匹配；底层模块继续负责证据摘要、审计与写入前检查。

## 当前接通范围

- 淘宝 `run` 调用现有 `project_scheduler.py --mode codex`，处理逐商品语义选择、ASR、物理方案、人物审核和项目质量审核。该链结束后调度器明确返回 `BLOCKED_UNMIGRATED`：当前项目调度器没有把通过的成品方案转换为统一逐款 Resolve 写入/回读事务的适配器。
- 都督当前是测试流程。现有 `reusable_test_delivery.py` 已支持单个测试批次最多 3 款，逐款追加并回读后才允许下一款；清空目标也经过该测试入口自己的身份、备份和授权门禁。当前缺口是 `dudu_scheduler.py` 仍调用单款 `delivery_pipeline.py`，尚未把冷启动检查、测试批次计划与 `reusable_test_delivery.py` 接成可恢复的批次状态机。
- `plan` 只记录并显示模式、商品范围、阶段清单和最后已接通阶段；不会分析媒体或连接 Resolve。
- `diagnose` 读取批次调度事件与商品检查点，报告可复用阶段和安全恢复点。都督遇到已创建的 Resolve 写入事务时优先 `recover`，禁止盲目重放。

## 调度器边界

淘宝商品的运行顺序是“字幕语义组合 → Codex 语义终审 → 首尾切点局部 ASR → 最终方案人物审核 → 本地硬门禁 → Resolve 写入/回读”。语义回执绑定精确的 rough selection 摘要；写入前不再重复语义终审。ASR 只转写首尾切点周围的短窗口。人物比例超限时只返修相关版本，未变版本与身份匹配的 ASR/画面缓存继续复用。

共享代码只负责路由、阶段顺序、批次恢复与错误定位。淘宝与都督保留各自独立的策略和阶段图；需要增加阶段时改对应模式图，需要修复算法时改相应底层模块。JSON 用于项目配置、配方和运行回执，不承担流程控制逻辑。

此版本是双入口和现有模块路由的第一步，不代表两个端到端闭环都已完成。都督需要接通已有的测试批次逐款事务；淘宝还缺把审核通过方案接入相符的 Resolve 写入/回读事务。交付适配器缺失时必须报告阻断阶段，不能把质量审核通过报告成成片交付完成。
